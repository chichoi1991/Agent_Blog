대규모 언어 모델은 상태를 유지하지 않습니다. 대화가 시작될 때마다 아무것도 모르는 상태에서 출발합니다. 메모리는 연속성이 있는 것처럼 보이도록 모델에 더하는 엔지니어링이며, 에이전트를 영리한 도구에서 동료에 가까운 존재로 바꿔 줍니다.

## 에이전트에 메모리가 필요한 이유

언어 모델은 지금 눈앞에 있는 내용만 알고 있습니다. 창을 닫고 새 창을 열면 설명한 선호 사항, 두 번이나 바로잡은 파일 이름 규칙, 3월에 바뀐 재무 승인 담당자 같은 정보가 모두 사라집니다. 매 세션은 처음 만난 사람처럼 시작합니다.

검색창이라면 괜찮습니다. 함께 일하는 동료라면 곤란하죠.

과학자가 실제로 일하는 모습을 생각해 보세요. 프로젝트 도중에 "지난 화요일에 뭘 해 봤더라?"라고 자문합니다. 향수 때문이 아니라, 이미 실패한 실험을 반복하느라 한 주를 허비하지 않기 위해서입니다. 답은 실험 노트에 있습니다. 그리고 그 노트가 유용한 것은 무엇을 **기록할 가치가 있는지**, 나중에 **어떻게 적절한 페이지를 찾을지**, 더는 사실이 아닌 내용을 언제 **지울지**를 잘 판단하기 때문입니다.

무엇을 기록할지, 무엇을 회상할지, 무엇을 잊을지는 에이전트의 메모리 시스템이 해결해야 하는 바로 그 세 가지 문제입니다.

| 메모리 없는 세션 | 메모리가 있는 세션 |
|---|---|
| 세션 1에서 맥락을 학습합니다. | 세션 1이 지속성 메모리 저장소에 기록합니다. |
| 세션 2는 처음부터 시작합니다. | 세션 2는 저장된 내용을 회상하고 이어서 작업합니다. |
| 세션 3도 처음부터 시작합니다. | 세션 3도 저장된 내용을 회상하고 이어서 작업합니다. |

_연속성의 차이. 메모리가 없으면 각 세션은 이전 세션과 단절됩니다. 메모리가 있어야 지식이 단일 대화의 경계를 넘어갑니다._

## 두 가지 시간 범위: 단기 메모리와 장기 메모리

### 단기 메모리는 실시간 컨텍스트 창입니다

단기 메모리는 에이전트가 지금 당장 조회하지 않고 볼 수 있는 모든 것입니다. 현재 대화, 최근 도구 결과, 진행 중인 추론이 여기에 해당합니다. 바로 접근할 수 있고 비용이 들지 않지만 용량은 한정되어 있습니다. 대화는 길어지지만 컨텍스트 창은 그렇지 않습니다.

엔지니어링 관점의 해법은 **압축(compaction)**입니다. 대화가 한도에 가까워지면 오래된 대화를 진행 중인 요약으로 압축하고 최근 대화는 원문 그대로 유지합니다. 사용자가 직접 요청하거나 런타임이 컨텍스트 압력이 임계값을 넘었을 때 자동으로 압축할 수 있습니다. 어느 쪽이든 모든 단어를 유지하지 않으면서 대화의 흐름을 보존합니다.

### 장기 메모리는 세션 외부에 유지됩니다

압축은 한 대화 안의 공간을 확보하지만 다음 대화에는 도움이 되지 않습니다. 장기 메모리는 세션이 끝난 뒤에도 남는 지식이므로 파일 저장소, 데이터베이스, 인덱스처럼 지속성 있는 곳에 저장해야 합니다. 런타임은 대화 중과 대화 후에 저장소에 **기록**하고, 필요할 때 관련 내용을 컨텍스트로 **가져오는** 두 가지 일을 합니다.

| | 단기 메모리 | 장기 메모리 |
|---|---|---|
| **무엇인가요?** | 실시간 컨텍스트 창 | 세션 외부에 저장된 지식 |
| **무엇이 들어 있나요?** | 현재 대화, 최근 도구 결과, 진행 중인 추론 | 일화적·의미적·절차적 지식 |
| **수명** | 휘발성, 창을 닫으면 사라짐 | 지속성, 세션이 바뀌어도 유지 |
| **접근** | 즉시 읽을 수 있지만 용량이 한정됨 | 의도적으로 기록한 다음 검색해야 함 |
| **핵심 기법** | 압축 | 기록과 회상 |

## 장기 메모리의 세 가지 종류

"장기 메모리"는 실제로는 서로 다른 세 가지 지식을 묶어 부르는 말입니다. 형성 방식과 사용 방식이 다르며, 안전 측면에서 중요한 위험도 서로 다릅니다.

| 종류 | 설명 | 예시 |
|---|---|---|
| **일화적(경험)** | 언제, 어디서, 어떻게 일어났는지에 대한 과거 사건 기록. 날짜가 적힌 일기 항목처럼 생각할 수 있습니다. | *화요일:* 사용자가 주문 XYZ의 환불을 요청했고, 담당자가 관리자에게 이관했습니다. |
| **의미적(사실)** | 일화적 기억을 추려 만든 지식. 사실이 바뀌었는지 감지하는 일도 필요합니다. | *경험:* "Alice가 베를린으로 이사한다고 했습니다." → *사실:* "Alice는 베를린에 삽니다." |
| **절차적(기술)** | 학습된 루틴, 워크플로, 경험칙으로, 에이전트의 근육 기억에 해당합니다. 정책을 아는 것과 그 정책에 따라 실행하는 것은 다릅니다. | *의미:* "500달러를 초과하는 경비는 승인이 필요합니다." *절차:* 영수증을 가져오고, 분류하고, 정책을 확인하고, 승인자에게 전달하고, 제출한 뒤 확인을 회신합니다. |

마지막 행은 곱씹어 볼 가치가 있습니다. 절차적 메모리는 에이전트가 필요할 때 실행할 수 있도록 검토된 루틴인 Skill과 가까운 개념입니다. [이제 에이전트에도 Skill이 있습니다](https://microsoft.github.io/mcscatblog/posts/modern-mcs-agent-skills/)를 읽어 봤다면, 반복 적용할 수 있게 포장된 노하우의 형태가 무엇인지 이미 알고 있을 겁니다.

> 도약은 에이전트가 사실을 안다는 데 있지 않습니다. 작업을 수행하는 방법을 안다는 데 있습니다.

## Copilot Studio의 메모리 접근 방식

[Copilot Studio의 메모리](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/memory-overview)는 구체적인 모델을 따릅니다. 에이전트는 Microsoft 관리형 저장소의 전용 폴더에 사용자 메모리를 파일로 저장합니다. 각 에이전트는 사용자마다 별도의 폴더를 유지하고, 상호 작용을 이어 가면서 그 폴더를 읽고 씁니다.

### 캡처, 저장, 적용

메모리의 수명 주기는 세 단계로 이루어집니다.

1. **캡처:** 대화에서 공유된 선호 사항과 관련 맥락 등의 신호를 에이전트가 기록합니다.
2. **저장:** 신호를 사용자의 전용 메모리 폴더에 파일로 저장합니다.
3. **적용:** 이후 상호 작용에서 해당 메모리를 읽어 응답이나 판단에 반영합니다.

메이커는 **빌드(Build)** 탭에서 에이전트의 메모리를 켤지 결정합니다. 메모리는 사용자별로 비공개이며 다른 사용자나 메이커는 볼 수 없습니다.

메모리는 사용자가 관리할 수도 있습니다. 메모리가 활성화된 에이전트와 새로운 채널에서 처음 상호 작용할 때, 에이전트 응답에 사용자 메모리 포털 링크가 포함됩니다. 포털은 새 브라우저 탭에서 열리며 사용자는 저장된 내용을 검토하거나 전체 메모리를 지울 수 있습니다. 채팅에서 에이전트에게 기억하는 내용을 설명하거나, 특정 메모리를 수정·삭제하거나, 포털 링크를 다시 표시해 달라고 요청할 수도 있습니다.

### 사용자별로 분리하고 보안 샌드박스에서 실행

설계에는 지속성 있는 경계가 두 가지 있습니다. 첫째, 모든 사용자는 각 에이전트에 대해 전용 메모리 폴더를 가지므로 한 사람의 맥락이 다른 사람과 공유되지 않습니다. 둘째, GitHub Copilot 하네스로 구동되는 에이전트는 Copilot Studio가 제공하는 [보안 샌드박스](https://learn.microsoft.com/en-us/microsoft-copilot-studio/harnesses-overview) 안에서 각 작업을 실행합니다.

| 경계 | 동작 |
|---|---|
| 사용자 메모리 | 사용자 A와 사용자 B는 한 에이전트에서 각자의 메모리 폴더를 사용합니다. |
| 작업 실행 | 에이전트 작업은 Copilot Studio가 제공하는 보안 샌드박스에서 실행됩니다. |

_명확한 경계. 에이전트의 메모리는 사용자별로 분리되며, 에이전트 작업은 격리된 환경에서 실행됩니다._

이 입문 글에서 중요한 경계는 두 가지입니다. 메모리는 사용자별로 분리되고 작업 실행은 격리됩니다.

### 더 넓은 메모리 패턴으로서의 성찰

캡처, 저장, 적용은 메모리가 이후 상호 작용을 어떻게 지원하는지 설명합니다. **성찰(reflection)**은 한 걸음 더 나아간, 메모리 시스템의 폭넓은 설계 패턴입니다.

성찰 루프에서 에이전트는 실시간 대화 밖에서 저장된 경험을 다시 살펴봅니다. 중요한 내용을 통합하고, 중복을 합치고, 오래된 정보를 갱신하고, 더는 유용하지 않은 내용을 폐기합니다. 매 항목을 영구적인 진실로 취급하는 대신 과학자가 주말에 실험 노트를 검토하는 것과 같습니다.

| 단계 | 동작 |
|---|---|
| 관찰 | 대화를 살펴봅니다. |
| 기록 | 보존할 가치가 있는 내용을 씁니다. |
| 성찰 | 실시간 대화 차례 밖에서 메모리를 검토합니다. |
| 적용 | 이후 대화에서 메모리를 활용합니다. |
| 폐기 | 오래된 내용은 수정하거나 제거합니다. |

_개념적인 성찰 루프. 메모리를 만드는 일은 시스템의 절반일 뿐입니다. 메모리를 유용하고 최신 상태로 유지하는 일도 중요합니다._

## 신뢰하되 검증하기

앞서 설명한 Copilot Studio의 동작은 실제 환경에서도 제대로 작동해야 합니다. 메모리를 더 많은 고객에게 제공하기 전에 엔지니어링 및 데이터 과학 팀이 이를 검증해야 합니다. 이 작업은 메이커가 혼자 알아서 하도록 맡기는 것이 아닙니다.

> 기억력이 나쁜 에이전트는 오류를 내며 멈추지 않습니다. 자신만만하게 틀릴 뿐입니다.

메모리를 신중하게 테스트해야 하는 이유는 실패가 눈에 잘 띄지 않기 때문입니다. 따라서 메모리가 도움이 되는 경우뿐 아니라 잘못될 수 있는 방식도 평가합니다. 에이전트에게 기대하는 동작은 다음과 같습니다.

- **회상:** 며칠 뒤 새로운 대화에서 에이전트는 전달받은 내용을 기억하나요?
- **부정적 회상:** 메모리에 오래되었거나 틀린 내용이 있을 때, 에이전트는 이를 알아차리나요, 아니면 자신만만하게 반복하나요?
- **답변 유보:** 실제로 들은 적 없는 내용에 대해 모른다고 말하나요? 그럴듯한 추측을 위해 올바른 거절을 포기하는 에이전트는 신뢰성이 높아진 것이 아니라 낮아진 것입니다.
- **환각:** 메모리가 있다는 사실 때문에 모델이 메모리에 없던 세부 내용을 만들어 내지는 않나요?

이처럼 섬세한 동작을 규명하는 것 자체가 하나의 분야입니다. 더 자세히 알고 싶다면 [LLM으로 에이전트 동작 평가하기](https://microsoft.github.io/mcscatblog/posts/better-llm-scoring/)를 참고하세요. 기준은 간단합니다. 메모리는 회상 능력을 분명히 향상하면서도 "모르겠습니다"라고 말할 의지를 해치지 않아야 합니다.

> 좋은 메모리 시스템은 더 많이 기억해서 좋은 것이 아닙니다. 올바른 내용을 기억하고, 모르는 것이 무엇인지 아는 시스템이 좋은 시스템입니다.

## 에이전트를 사용하는 사람에게 의미하는 것

아키텍처를 걷어 내면 메모리가 제공하는 가치는 하나입니다. **사람들이 같은 말을 반복하지 않아도 되는 에이전트**입니다.

지원 에이전트는 고객이 이미 두 번이나 담당자에게 이관됐다는 사실을 기억하고 처음부터 다시 설명하게 하지 않습니다. 운영 에이전트는 특정 승인이 늘 두 번째 서명을 필요로 한다는 사실을 기억해 다시 묻지 않습니다. 분석가의 에이전트는 지난 분기에 어떤 접근 방식을 시도했고 왜 포기했는지 기억합니다. 각각은 작아 보이지만 수백 번의 대화에 쌓이면 사람들이 마지못해 쓰는 도구와 믿고 의지하는 동료의 차이가 됩니다.

메이커가 메모리 엔지니어가 되지 않아도 이런 가치를 얻을 수 있습니다. 메이커는 에이전트의 메모리를 켤지 결정합니다. 그러면 Copilot Studio가 관련 맥락을 캡처하고 사용자별로 따로 저장해 이후 상호 작용에 적용합니다. 사용자는 채팅이나 메모리 포털에서 자신의 메모리를 확인하고 관리할 수 있습니다.

에이전트는 진정한 동료가 되어 가고 있습니다. 무엇을 기록하고, 어떻게 다시 찾고, 무엇을 놓아줄지 결정하는 메모리가 그 관계를 이어 갈 가치가 있게 합니다.

그렇다면 여러분의 에이전트가 가장 먼저 잊지 않기를 바라는 것은 무엇인가요?

> Copilot Studio의 메모리는 GitHub Copilot 하네스로 구동되는 에이전트를 위한 프로덕션 준비 미리 보기입니다. 미리 보기 기능과 설명서는 변경될 수 있습니다.
