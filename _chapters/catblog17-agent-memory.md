대규모 언어 모델은 상태를 유지하지 않습니다. 대화가 시작될 때마다 모든 것이 처음부터 시작됩니다. 메모리는 연속성이 있는 것처럼 보이게 모델을 둘러싸는 엔지니어링이며, 에이전트를 똑똑한 도구에서 동료에 가까운 존재로 바꿔 줍니다.

## 에이전트에 메모리가 필요한 이유

언어 모델은 지금 눈앞에 있는 정보만 압니다. 창을 닫고 새 창을 열면 사용자가 설명한 선호 사항, 두 번이나 바로잡은 파일 이름 규칙, 3월에 바뀐 재무 승인 담당자까지 모두 사라집니다. 모든 세션은 낯선 사람과 다시 시작하는 것과 같습니다.

검색창이라면 괜찮습니다. 동료라면 곤란합니다.

과학자가 실제로 일하는 방식을 생각해 보세요. 프로젝트 중간에 과학자는 *지난 화요일에 무엇을 시도했더라?* 하고 자문합니다. 향수가 아니라 이미 실패한 실험을 반복하느라 일주일을 낭비하지 않기 위해서입니다. 답은 실험 노트에 있습니다. 그리고 그 노트가 제 역할을 하려면 무엇을 **기록할 가치가 있는지**, 나중에 **어떻게 찾아야 하는지**, 더 이상 사실이 아닌 내용을 언제 **지워야 하는지**를 알아야 합니다.

무엇을 기록하고, 무엇을 떠올리고, 무엇을 잊을지 결정하는 이 세 가지 문제는 에이전트의 메모리 시스템이 풀어야 하는 문제와 같습니다.

| 메모리 없음 | 메모리 있음 |
|---|---|
| 세션 1에서 맥락을 배우지만 세션 2와 3은 처음부터 시작합니다. | 세션 1이 지속 메모리 저장소에 기록하고, 세션 2와 3이 이를 불러와 이어서 작업합니다. |

## 두 가지 시간 범위: 단기 기억과 장기 기억

### 단기 기억은 현재의 컨텍스트 창입니다

단기 기억은 에이전트가 지금 바로 볼 수 있는 모든 것입니다. 현재 대화, 최근 도구 결과, 진행 중인 추론이 여기에 포함됩니다. 즉시 이용할 수 있지만 용량은 유한합니다. 대화는 길어지지만 컨텍스트 창은 늘어나지 않습니다.

엔지니어링에서는 **압축(compaction)**으로 대응합니다. 대화가 한도에 가까워지면 오래된 대화를 실행 요약으로 압축하고 최근 대화는 그대로 둡니다. 압축은 사용자가 직접 요청하거나 런타임이 컨텍스트 압박이 임계값을 넘었을 때 자동으로 시작할 수 있습니다. 어느 쪽이든 모든 단어를 보존하지 않고 대화의 흐름을 이어갑니다.

### 장기 기억은 세션이 끝나도 유지됩니다

압축은 한 대화 안에 여유를 만들지만 다음 대화에는 영향을 주지 않습니다. 장기 기억은 세션이 끝난 뒤에도 남는 지식이므로 파일 저장소, 데이터베이스, 인덱스 같은 지속 저장소가 필요합니다. 런타임은 대화 중이나 이후에 저장소에 **기록**하고, 필요할 때 관련 내용을 컨텍스트로 **가져오는** 두 가지 일을 합니다.

| 구분 | 단기 기억 | 장기 기억 |
|---|---|---|
| **무엇인가요?** | 현재의 컨텍스트 창 | 세션 외부에 저장된 지식 |
| **무엇이 있나요?** | 현재 대화, 최근 도구 결과, 진행 중인 추론 | 일화·의미·절차 지식 |
| **수명** | 휘발성으로 창을 닫으면 사라짐 | 세션 사이에도 유지 |
| **접근** | 바로 읽을 수 있지만 용량이 유한함 | 의도적으로 기록한 뒤 가져와야 함 |
| **핵심 기법** | 압축 | 기록과 회상 |

## 장기 기억의 세 가지 유형

“장기 기억”은 실제로 서로 다른 세 가지 지식 유형을 아우르는 말입니다. 각 유형은 형성되고 사용되는 방식이 다르며, 안전 측면에서 위험도 다릅니다.

| 유형 | 설명 | 예 |
|---|---|---|
| **일화 기억**(경험) | 언제, 어디서, 어떻게 일어났는지 등 특정 과거 사건에 대한 기록입니다. 날짜가 적힌 일기 항목과 비슷합니다. | *화요일:* 사용자가 주문 XYZ 환불을 요청해 담당 관리자에게 전달했다. |
| **의미 기억**(사실) | 일화 기억을 정제한 것입니다. 경험을 지속적인 사실로 바꾸며, 그 사실이 새 정보로 대체되었는지도 알아차려야 합니다. | *경험:* “Alice가 베를린으로 이사한다고 말했다.” → *사실:* “Alice는 베를린에 산다.” |
| **절차 기억**(기술) | 학습된 루틴, 워크플로, 경험에서 얻은 규칙입니다. 정책을 아는 것과 그 정책에 따라 실행하는 방법을 아는 것의 차이입니다. | *의미:* “500달러를 초과하는 비용은 승인이 필요하다.” *절차:* 영수증을 가져오고, 분류하고, 정책을 확인하고, 승인 담당자에게 전달하고, 제출한 뒤 확인한다. |

마지막 행을 눈여겨볼 만합니다. 절차 기억은 에이전트가 필요할 때 실행할 수 있도록 검토된 루틴인 Skill과 가깝습니다. [이제 에이전트에도 Skill이 있습니다](https://microsoft.github.io/mcscatblog/posts/modern-mcs-agent-skills/)를 읽었다면 그 형태를 알고 있을 겁니다. 다시 적용할 수 있도록 포장된 노하우입니다.

> 중요한 도약은 에이전트가 사실을 안다는 데 있지 않습니다. 작업을 수행하는 방법까지 안다는 데 있습니다.

## Copilot Studio의 메모리 접근 방식

[Copilot Studio의 메모리](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/memory-overview)는 구체적인 모델을 따릅니다. 에이전트는 Microsoft 관리 저장소의 전용 폴더에 사용자 메모리를 파일로 저장합니다. 각 에이전트는 사용자별로 별도의 폴더를 유지하고, 상호 작용 전반에 걸쳐 해당 폴더에서 읽고 씁니다.

### 수집, 저장, 적용

메모리는 다음 세 단계로 관리됩니다.

1. **수집(Capture)**: 대화 중 공유된 선호 사항이나 관련 맥락과 같은 신호를 에이전트가 기록합니다.
2. **저장(Store)**: 해당 신호를 사용자의 전용 메모리 폴더에 파일로 저장합니다.
3. **적용(Apply)**: 이후 상호 작용에서 에이전트가 메모리를 읽어 응답이나 판단에 활용합니다.

메이커는 **빌드(Build)** 탭에서 에이전트의 메모리 사용 여부를 결정합니다. 메모리는 사용자 개인에게만 공개되며 다른 사용자나 메이커는 볼 수 없습니다.

메모리는 사용자가 관리할 수도 있습니다. 메모리 사용 에이전트와 새 채널에서 처음 상호 작용하면 에이전트 응답에 해당 사용자의 메모리 포털 링크가 포함됩니다. 포털은 새 브라우저 탭에서 열리며, 사용자는 저장된 내용을 확인하거나 모든 메모리를 지울 수 있습니다. 채팅에서 기억하는 내용을 설명하거나, 특정 메모리를 업데이트하거나, 잊어 달라고 요청하거나, 포털 링크를 다시 표시해 달라고 할 수도 있습니다.

### 사용자별 분리와 보안 샌드박스 실행

설계에는 두 가지 지속적인 경계가 있습니다. 첫째, 에이전트마다 사용자별 전용 메모리 폴더가 있어 한 사용자의 맥락을 다른 사용자와 공유하지 않습니다. 둘째, GitHub Copilot 하네스로 구동되는 에이전트는 Copilot Studio가 제공하는 [보안 샌드박스](https://learn.microsoft.com/en-us/microsoft-copilot-studio/harnesses-overview)에서 각 작업을 실행합니다.

| 경계 | 동작 |
|---|---|
| 메모리 | 사용자 A와 사용자 B는 에이전트별로 각각 분리된 메모리 폴더를 사용합니다. |
| 작업 실행 | 에이전트 작업은 Copilot Studio가 제공하는 보안 샌드박스에서 실행됩니다. |

이 입문 글에서 중요한 경계는 사용자별 메모리 분리와 작업 실행 격리입니다.

### 더 넓은 메모리 패턴으로서의 회고

수집, 저장, 적용은 메모리가 향후 상호 작용을 지원하는 방식을 설명합니다. **회고(Reflection)**는 한 단계 더 나아간 메모리 시스템 설계 패턴입니다.

회고 루프에서 에이전트는 현재 대화 밖에서 저장된 경험을 다시 살펴보고, 중요한 정보를 정리하고, 중복을 합치고, 오래된 정보를 업데이트하고, 더 이상 유용하지 않은 정보를 폐기합니다. 매주 실험 노트를 검토해 모든 기록을 영구적인 사실로 취급하지 않는 과학자의 방식과 비슷합니다.

| 단계 | 설명 |
|---|---|
| 관찰 | 대화를 살펴봅니다. |
| 기록 | 남길 가치가 있는 내용을 기록합니다. |
| 회고 | 현재 대화가 끝난 뒤 내용을 정리합니다. |
| 적용 | 이후 대화에서 기억을 활용합니다. |
| 폐기 | 오래되었거나 틀린 기억을 수정하거나 제거합니다. |

기억을 만드는 것은 시스템의 절반일 뿐입니다. 기억을 유용하고 최신 상태로 유지하는 것도 중요합니다.

## 신뢰하되 검증하기

앞서 설명한 Copilot Studio의 동작이 실제 환경에서도 기대대로 작동해야 합니다. 메모리를 더 많은 고객에게 제공하기 전에 엔지니어링 및 데이터 과학 팀이 이를 검증해야 합니다. 메이커가 혼자 해결하도록 맡길 일이 아닙니다.

> 기억력이 나쁜 에이전트는 오류로 중단되지 않습니다. 자신 있게 틀릴 뿐입니다.

이 때문에 메모리의 실패 방식까지 고려해 신중히 테스트해야 합니다. 에이전트가 도움이 되는지만이 아니라 잘못될 수 있는 방식도 평가합니다.

- **회상**: 며칠 뒤 완전히 새 대화에서도 에이전트가 전달받은 내용을 기억합니까?
- **부정적 회상**: 오래되었거나 틀린 정보가 메모리에 있을 때 이를 알아차립니까, 아니면 자신 있게 반복합니까?
- **답변 보류**: 실제로 들은 적 없는 내용에 대해 모른다고 말합니까? 그럴듯한 추측을 위해 올바른 거절을 포기하는 에이전트는 더 신뢰할 수 있는 것이 아닙니다.
- **환각**: 메모리가 있으면 모델이 메모리에 없는 세부 정보를 만들어 내게 됩니까?

이처럼 미묘한 동작을 구체적으로 평가하는 일은 별도의 분야입니다. 자세한 내용은 [LLM으로 에이전트 동작 점수 매기기](https://microsoft.github.io/mcscatblog/posts/better-llm-scoring/)를 참고하세요. 기준은 간단합니다. 메모리는 회상을 분명히 돕되, “모르겠습니다”라고 말하는 능력을 해쳐서는 안 됩니다.

> 좋은 메모리 시스템은 더 많이 기억하는 시스템이 아닙니다. 올바른 것을 기억하고, 모르는 것이 무엇인지 아는 시스템입니다.

## 에이전트를 사용하는 사람에게 의미하는 것

아키텍처를 걷어내면 메모리가 제공하는 가치는 하나입니다. **사람들이 같은 말을 반복하지 않아도 되는 에이전트**입니다.

지원 에이전트는 고객이 이미 두 번 에스컬레이션되었다는 사실을 기억해 처음부터 다시 설명하게 하지 않습니다. 운영 에이전트는 이 승인에 항상 두 번째 서명이 필요하다는 점을 기억해 재차 묻지 않습니다. 분석가의 에이전트는 지난 분기에 어떤 접근을 시도했고 왜 중단했는지 떠올립니다. 각각은 작은 변화지만 수백 번의 대화에 쌓이면 사람들이 마지못해 쓰는 도구와 믿고 의지하는 동료의 차이를 만듭니다.

메이커가 메모리 엔지니어가 되지 않아도 이런 가치를 얻을 수 있습니다. 메이커는 에이전트의 메모리 사용 여부를 정하고, Copilot Studio는 관련 맥락을 수집해 사용자별로 따로 저장한 뒤 이후 상호 작용에 적용합니다. 사용자는 채팅이나 메모리 포털에서 자신의 메모리를 확인하고 관리할 수 있습니다.

에이전트는 진정한 동료가 되어 가고 있습니다. 무엇을 기록하고, 어떻게 다시 찾고, 무엇을 잊을지 결정하는 메모리가 그 관계를 가치 있게 만듭니다.
