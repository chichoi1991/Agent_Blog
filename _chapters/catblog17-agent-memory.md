대규모 언어 모델은 상태를 유지하지 않습니다. 대화가 시작될 때마다 아무것도 모르는 상태에서 출발합니다. 메모리는 연속성이 있는 듯한 경험을 만들기 위해 모델에 덧붙이는 엔지니어링이며, 에이전트를 똑똑한 도구에서 동료에 가까운 존재로 바꿔 줍니다.

## 에이전트에 메모리가 필요한 이유

언어 모델은 지금 눈앞에 있는 정보만 압니다. 창을 닫고 새 창을 열면 모든 것이 사라집니다. 설명했던 선호 사항, 두 번이나 수정해 준 파일 이름 규칙, 3월에 재무 승인 담당자가 바뀌었다는 사실도 모두 잊습니다. 매 세션은 낯선 사람과 다시 시작하는 것과 같습니다.

검색창에는 괜찮을 수 있지만, 함께 일하는 동료에게는 적합하지 않습니다.

과학자가 실제로 일하는 방식을 생각해 보세요. 프로젝트 중간에 과학자는 *지난 화요일에 무엇을 시도했지?*라고 자문합니다. 추억에 잠기려는 것이 아니라, 이미 실패한 실험을 반복하느라 한 주를 낭비하지 않기 위해서입니다. 답은 연구 노트에 있습니다. 그리고 그 노트가 쓸모 있는 이유는 과학자가 세 가지를 능숙하게 해내기 때문입니다. **기록할 가치가 있는 것이 무엇인지**, 나중에 **필요한 페이지를 어떻게 찾을지**, 더 이상 사실이 아닌 내용을 **언제 지워야 할지** 아는 것입니다.

무엇을 기록하고, 무엇을 떠올리고, 무엇을 잊을지. 에이전트 메모리 시스템도 바로 이 세 가지 문제를 해결해야 합니다.

```text
메모리가 없을 때                    메모리가 있을 때
세션 1: 맥락을 학습                  세션 1
세션 2: 처음부터 시작                     |
세션 3: 처음부터 시작                영구 메모리 저장소
                                           |       |
                                  세션 2: 기억하고 확장
                                  세션 3: 기억하고 확장
```
_연속성의 간극. 메모리가 없으면 각 세션은 이전 세션과 단절됩니다. 메모리는 지식이 단일 대화의 경계를 넘어 이어지게 합니다._

## 두 가지 시간 범위: 단기와 장기

### 단기 메모리는 현재의 컨텍스트 창입니다

단기 메모리는 에이전트가 별도로 찾아보지 않고 *지금* 볼 수 있는 모든 것입니다. 현재 대화, 최근 도구 결과, 진행 중인 추론이 여기에 포함됩니다. 즉시 접근할 수 있지만 용량은 한정되어 있습니다. 대화는 길어지지만 컨텍스트 창은 그렇지 않습니다.

엔지니어링 측면의 해결책은 **압축(compaction)**입니다. 대화가 한계에 가까워지면 오래된 대화 차례를 진행 중인 요약으로 압축하고 최근 대화는 원문 그대로 유지합니다. 압축은 사용자가 직접 실행하거나, 컨텍스트 사용량이 임계값을 넘었을 때 런타임이 자동으로 실행하는 방식으로 시작됩니다. 어느 쪽이든 모든 단어를 보존하지 않고도 대화의 맥락을 이어 갈 수 있습니다.

### 장기 메모리는 세션 밖에서도 유지됩니다

압축은 한 대화 안의 공간을 확보하지만 다음 대화까지 이어 주지는 않습니다. 장기 메모리는 세션이 완전히 끝난 뒤에도 남는 지식이므로 파일 저장소, 데이터베이스, 인덱스처럼 지속성 있는 곳에 저장해야 합니다. 런타임은 대화 중과 대화 후에 그 저장소에 **기록**하고, 필요할 때 관련 내용을 컨텍스트로 **검색**하는 두 가지 일을 합니다.

| 구분 | 단기 메모리 | 장기 메모리 |
|---|---|---|
| **무엇인가요?** | 현재의 컨텍스트 창 | 세션 외부에 저장된 지식 |
| **무엇이 담기나요?** | 현재 대화, 최근 도구 결과, 진행 중인 추론 | 일화적·의미적·절차적 지식 |
| **지속 기간** | 휘발성, 창을 닫으면 사라짐 | 지속성 있음, 세션을 넘어 유지 |
| **접근 방식** | 즉시 무료로 읽을 수 있지만 용량이 한정됨 | 의도적으로 기록한 뒤 검색해야 함 |
| **핵심 기법** | 압축 | 기록과 회상 |

## 세 가지 장기 메모리 유형

"장기 메모리"는 실제로 서로 다른 세 가지 지식을 아우르는 말입니다. 각각 형성되는 방식과 사용 방식이 다르고, 특히 안전 측면에서 위험도 다릅니다.

| 유형 | 의미 | 예시 |
|---|---|---|
| **일화적**(경험) | 언제, 어디서, 어떻게 일어났는지에 관한 구체적인 과거 기록입니다. 날짜가 적힌 일기 항목과 비슷합니다. | *화요일:* 사용자가 주문 XYZ의 환불을 요청했고, 나는 담당 관리자에게 전달했다. |
| **의미적**(사실) | 일화적 기억을 요약해 얻은 사실입니다. 경험을 지속적인 사실로 정리하며, 그 사실이 새 정보로 대체되었는지도 알아차려야 합니다. | *경험:* "Alice가 베를린으로 이사한다고 했다." → *사실:* "Alice는 베를린에 산다." |
| **절차적**(기술) | 학습한 절차, 워크플로, 경험칙입니다. 에이전트의 몸에 밴 기술과 같습니다. 정책을 아는 것과 그 정책에 따라 실제로 처리하는 것은 다릅니다. | *의미적:* "500달러 초과 비용은 승인이 필요하다." *절차적:* 영수증을 가져오고, 분류하고, 정책과 대조하고, 승인 담당자에게 보내고, 기록한 뒤 확인을 회신한다. |

마지막 행을 눈여겨볼 만합니다. 절차적 메모리는 필요할 때 실행할 수 있도록 검토·정리된 루틴인 Skill과 가깝습니다. [Agents Have Skills Now](https://microsoft.github.io/mcscatblog/posts/modern-mcs-agent-skills/)를 읽었다면 그 형태를 알고 있을 것입니다. 다시 적용할 수 있도록 패키징된 노하우입니다.

> 중요한 도약은 에이전트가 사실을 안다는 데 있지 않습니다. 작업을 어떻게 해야 하는지도 안다는 데 있습니다.

## Copilot Studio의 메모리 접근 방식

[Copilot Studio의 메모리](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/memory-overview)는 의도적으로 구체적인 모델을 따릅니다. 에이전트는 Microsoft 관리형 저장소의 전용 폴더에 사용자 메모리를 파일로 저장합니다. 에이전트마다 사용자별 폴더가 따로 있으며, 에이전트는 상호작용을 이어 가며 그 폴더에서 읽고 씁니다.

### 수집, 저장, 적용

메모리는 세 단계로 진행됩니다.

1. **수집(Capture)**: 에이전트가 대화에서 공유된 선호 사항이나 관련 맥락 같은 신호를 기록합니다.
2. **저장(Store)**: 신호를 사용자의 전용 메모리 폴더에 파일로 저장합니다.
3. **적용(Apply)**: 이후 상호작용에서 에이전트가 해당 메모리를 읽고 응답이나 결정에 활용합니다.

메이커는 **Build** 탭에서 에이전트의 메모리 사용 여부를 결정합니다. 메모리는 사용자 개인에게만 공개됩니다. 다른 사용자와 메이커는 볼 수 없습니다.

메모리는 사용자가 직접 관리할 수도 있습니다. 메모리가 활성화된 에이전트와 새로운 채널에서 처음 상호작용하면, 에이전트 응답에 해당 사용자의 메모리 포털 링크가 포함됩니다. 포털은 새 브라우저 탭에서 열리며, 사용자는 에이전트가 저장한 내용을 검토하거나 모든 메모리를 지울 수 있습니다. 채팅에서 에이전트에게 기억하는 내용을 설명하거나 특정 메모리를 업데이트·삭제하도록 요청하고, 포털 링크를 다시 표시해 달라고 할 수도 있습니다.

### 사용자별 분리와 보안 샌드박스 실행

설계에는 지속적으로 지켜지는 두 가지 경계가 있습니다. 첫째, 에이전트마다 사용자별 메모리 폴더가 따로 있어 한 사용자의 맥락이 다른 사용자와 공유되지 않습니다. 둘째, GitHub Copilot 하네스로 구동되는 에이전트는 Copilot Studio가 제공하는 [보안 샌드박스](https://learn.microsoft.com/en-us/microsoft-copilot-studio/harnesses-overview) 안에서 각 작업을 실행합니다.

```text
한 에이전트의 메모리                  작업 실행
사용자 A -> 전용 메모리 폴더           에이전트 작업
사용자 B -> 전용 메모리 폴더                |
                                      Copilot Studio가 제공하는
                                         보안 샌드박스
```
_명확한 경계. 에이전트의 사용자별 메모리는 분리되고, 작업 실행은 격리됩니다._

이 소개 글에서 중요한 경계는 여기까지입니다. 메모리는 사용자별로 분리되고 작업 실행은 격리됩니다.

### 더 폭넓은 메모리 패턴으로서의 성찰

수집, 저장, 적용은 메모리가 이후 상호작용을 지원하는 방식을 설명합니다. **성찰(reflection)**은 여기서 한 걸음 더 나아간, 더 폭넓은 메모리 시스템 설계 패턴입니다.

성찰 루프에서 에이전트는 실시간 대화 바깥에서 저장된 경험을 다시 살펴봅니다. 중요한 정보를 통합하고, 중복을 합치고, 오래된 정보를 업데이트하고, 더는 유용하지 않은 정보를 정리합니다. 모든 기록을 영구적인 진실로 취급하지 않고 한 주가 끝날 때 과학자의 연구 노트를 다시 살펴보는 것과 같습니다.

```text
관찰(대화) -> 기록(남길 가치가 있는 내용) -> 성찰(실시간 대화 밖)
    ^                                             |
    |                                             v
정리(오래된 정보) <- 적용(이후 대화) <-----------+
        |
        +-- 수정되거나 삭제된 내용은 다음 관찰에 반영
```
_개념적인 성찰 루프. 메모리를 만드는 것만큼 메모리를 유용하고 최신 상태로 유지하는 일도 중요합니다._

## 신뢰하되 검증하기

위에서 설명한 Copilot Studio의 동작은 실제 환경에서도 제대로 작동해야 합니다. 메모리 기능을 더 많은 고객에게 제공하기 전에 엔지니어링 및 데이터 과학 팀이 이를 검증해야 합니다. 메이커가 직접 알아서 해결하도록 맡길 일이 아닙니다.

> 메모리가 나쁜 에이전트는 충돌하지 않습니다. 그저 확신에 차서 틀린 답을 할 뿐입니다.

메모리의 실패 방식은 조용히 나타나므로 신중한 평가가 필요합니다. 메모리가 도움이 되는 경우뿐 아니라 잘못될 수 있는 방식도 평가합니다. 에이전트가 충족해야 하는 동작에는 다음이 포함됩니다.

- **회상(Recall).** 며칠 뒤 완전히 새로운 대화에서도 전달받은 내용을 기억하나요?
- **부정적 회상(Negative recall).** 메모리에 오래되었거나 잘못된 내용이 있을 때 이를 알아차리나요, 아니면 확신에 차서 반복하나요?
- **답변 보류(Abstention).** 실제로 들은 적 없는 내용이라면 모른다고 말하나요? 그럴듯한 추측을 위해 올바른 거부를 포기하는 에이전트는 더 신뢰할 만한 것이 아니라 덜 신뢰할 만합니다.
- **환각(Hallucination).** 메모리가 있다는 이유로 거기에 없던 세부 정보를 지어내나요?

이처럼 미묘한 동작을 구체적으로 평가하는 것 자체가 하나의 분야입니다. 자세한 내용은 [LLM으로 에이전트 동작 점수 매기기](https://microsoft.github.io/mcscatblog/posts/better-llm-scoring/)에서 설명합니다. 기준은 간단합니다. 메모리는 회상 능력을 확실히 높이되, "모르겠습니다"라고 말할 수 있는 에이전트의 태도를 해쳐서는 안 됩니다.

> 메모리 시스템은 더 많이 기억한다고 좋은 것이 아닙니다. 올바른 것을 기억하고, 모르는 것이 무엇인지 아는 시스템이 좋은 시스템입니다.

## 에이전트를 사용하는 사람들에게 주는 의미

아키텍처를 걷어 내고 보면 메모리가 주는 것은 하나입니다. **사람들이 같은 말을 되풀이하지 않아도 되는 에이전트**입니다.

지원 에이전트는 고객이 이미 두 번이나 상위 지원 단계로 전달되었다는 사실을 기억해 처음부터 다시 이야기를 묻지 않습니다. 운영 에이전트는 승인을 받으려면 항상 두 번째 서명이 필요하다는 점을 기억해 다시 확인하지 않습니다. 분석 에이전트는 지난 분기에 어떤 접근 방식을 시도했고 왜 중단했는지 떠올립니다. 각각은 작은 개선이지만, 수백 번의 대화에 쌓이면 사람들이 마지못해 쓰는 도구와 믿고 의지하는 동료의 차이가 됩니다.

메이커가 메모리 엔지니어가 되지 않아도 이런 가치를 얻을 수 있습니다. 메이커는 에이전트의 메모리 사용 여부를 결정하고, Copilot Studio가 관련 맥락을 수집해 사용자별로 저장한 다음 이후 상호작용에서 적용합니다. 각 사용자는 채팅이나 메모리 포털을 통해 자신의 메모리를 확인하고 관리할 수 있습니다.

에이전트는 진정한 동료가 되어 가고 있습니다. 무엇을 기록하고, 어떻게 다시 찾고, 무엇을 놓아줄지 결정하는 메모리가 그 관계를 가치 있게 만드는 요소입니다.

여러분의 에이전트가 가장 먼저 무엇을 잊지 않기를 바라나요?
