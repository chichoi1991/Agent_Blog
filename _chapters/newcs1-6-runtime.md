## 9.1 한 줄로 — 에이전트는 어디서 도는가

- **세션 = 1개의 격리 컨테이너.** 세션마다 새로 프로비저닝되고 종료되면 통째로 폐기됩니다.
- 이 컨테이너 안에서 LLM이 **최소 권한 사용자**로 에이전틱 루프를 돌리며 셸·검색·파일 보기/편집·**코드 실행** 같은 실제 도구를 호출합니다.
- 즉, "coding harness + CLI layer"가 **여기서 물리적으로 구현** 됩니다.

## 9.2 작업 공간의 구성 (개념)

컨테이너 안에서 에이전트가 쓰는 공간은 역할별로 나뉩니다(구체적 경로·내부 명칭은 비공개).

| 영역 | 역할 |
|---|---|
| **업로드 영역** | 참고자료 검색으로 내려받은 원본 파일 |
| **작업 영역** | 작업용 임시 파일·전처리 아티팩트 |
| **결과물 영역** | AI가 생성한 최종 산출물 — 사용자가 다운로드하는 공간 |
| **세션 메모리** | 대화 턴·체크포인트·검색 인덱스 등 세션 상태 |
| **스킬 영역** | 분석·문서 처리 스킬 스크립트 |
| **AI 엔진(보호 영역)** | 에이전트조차 접근할 수 없는 엔진 본체 |

## 9.3 보안·격리 모델 — "Sandbox"의 구현

```
최소 권한 사용자
   ↓ 접근 가능
 작업 공간(업로드/작업/결과물/스킬)
   ↓ 접근 차단 🔒
 AI 엔진 본체   ← 핵심 보호 영역
```

- 에이전트(LLM 주도)는 **최소 권한 사용자**로 동작하며, 작업·산출은 자기 작업 공간 안에서만 합니다.
- **엔진 본체는 에이전트조차 못 읽습니다.** 프롬프트 인젝션으로 에이전트가 탈취돼도 엔진·다른 세션엔 닿지 못합니다.
- 도구 장에서 말한 "같은 거버넌스 경계 안에서 실행"이 이 컨테이너 경계로 물리화된 것입니다.

> **비유:** 에이전트는 "샌드박스에서 노는 인턴", 엔진은 "잠긴 기계실"입니다. 인턴이 실수하거나 누가 인턴을 꾀어도 기계실 문은 안 열립니다.

## 9.4 참조자료 처리 — 가장 크게 개선된 부분

CLI·컨테이너 전환의 최대 수혜는 **참조자료(지식) 처리 방식**입니다.

**무엇이 달라졌나 — 스니펫에서 실파일로:**

1. 참조자료 검색(예: SharePoint 지식)은 여전히 **Graph 기반 검색**을 사용합니다 — 여기까진 동일.
2. **(신규)** 검색 결과 메타데이터로 *답변 + 다운로드 정보*를 함께 반환합니다.
3. **(신규)** 필요하면 그 정보로 **실제 파일을 컨테이너 작업 공간에 내려받아** 처리합니다.
4. **(신규)** 내려받은 파일을 **Python 라이브러리로 대용량 처리**합니다 — 코드를 짤 토큰만 충분하면 대용량 데이터도 문제없이.

→ 클래식이 *검색 스니펫* 만으로 답했다면, New CLI 에이전트는 **원본 파일 자체를 열어** 수만 행 엑셀·수백 쪽 PDF를 코드로 집계·변환합니다. **대용량 파일·코드 인터프리터 처리가 왜 가능한지**가 여기서 드러납니다.

**왜 클래식은 엑셀을 제대로 못 다뤘나 — RAG(검색 기반)의 한계:**

클래식 Copilot Studio는 파일을 **검색(RAG) 파이프라인**으로 처리했습니다.

```
사용자 질문
   ↓ 검색 쿼리 생성
검색 엔진 (AI Search / SharePoint Search)
   ↓ 청크(chunk) 단위 텍스트만 반환
LLM 컨텍스트에 청크 삽입 → 답변 생성
```

핵심은 **파일을 통째로 받지 않는다**는 것입니다.

- 파일을 미리 **인덱싱(벡터화)** 해두고
- 질문과 유사한 **청크(보통 512~2048 토큰)만 Top-K**로 꺼내 LLM에 투입
- 원본 파일에는 직접 접근하지 않음 ❌

그래서 엑셀처럼 **표 전체를 집계해야 답이 나오는 질문**에 구조적으로 약합니다. 행이 청크 경계로 잘리면 합계·평균이 어긋나고, 필요한 행이 Top-K에 안 들어오면 아예 답을 못 합니다.

**같은 질문, 다른 처리 — 근사치 vs 정확값:**

```
클래식(RAG):
  "제조사별 평균 가격은?"
  → 청크 검색 → 관련 텍스트 조각 → 근사치
  → 청크에 없으면 답 못함 ❌

New CLI(코드 실행):
  "제조사별 평균 가격은?"
  → Python: df.groupby('Manufacturer')['Price'].mean()
  → 전체 행 집계 → 정확한 수치 ✅ (정렬·필터도 가능)
```

**두 패러다임 비교:**

| 항목 | 클래식 Studio (RAG) | New CLI (코드 실행) |
|---|---|---|
| 파일 처리 | 청크 검색(인덱스 경유) | 다운로드 후 Python 직접 처리 |
| 원본 접근 | ❌ 인덱스 경유 | ✅ 직접 접근 |
| 대용량 | 청크 크기로 제한 | Python이 처리 → 유연 |
| 정확도 | 청크 누락 가능성 | 전체 데이터 집계 |
| 코드 실행 | ❌ 불가 | ✅ 가능 |
| 파일 생성 | ❌ 불가 | ✅ PPT·HTML·CSV 등 |
| 토큰 관리 | 청크로 자동 제한 | AI가 직접 관리 |

> **한 줄 정리:** 클래식은 **"검색 기반(RAG)"** — 파일을 인덱스로 바꿔 청크로 답합니다. New CLI는 **"실행 기반(Code+Tool)"** — 파일을 직접 받아 Python으로 정확히 처리합니다. 같은 M365 데이터에 닿지만 **처리 패러다임이 근본적으로 다릅니다.**

**그럼 대용량 파일을 받으면 토큰이 터지지 않나?:**

자연스러운 의문이지만 답은 "안 터진다" — 애초에 **LLM이 파일을 직접 읽지 않기 때문**입니다. xlsx·pptx·pdf 같은 **바이너리는 검색 스니펫이 비어** 있고 파일 위치만 옵니다(텍스트 문서만 일부 내용 포함). 그래서 LLM은 파일을 컨텍스트에 퍼붓는 대신 **Python에게 처리를 시킵니다.**

```python
# ❌ 나쁜 패턴: 파일 → LLM 컨텍스트 직접 투입 → 💥 토큰 초과
# ✅ 좋은 패턴: 파일 → Python 처리 → 결과 요약만 → LLM

df = pd.read_excel('large_file.xlsx')           # 파이썬 메모리에서 처리
result = df.groupby('col').agg({'val': 'sum'})  # 연산도 파이썬이
print(result)   # ← LLM이 읽는 건 이 요약(수십 토큰)뿐
```

보조 전략(자세한 건 2부·3부):

- **컬럼/시트 선택 로드** — `usecols`·`sheet_name`·`nrows`로 필요한 부분만
- **청크 처리** — `pd.read_csv(..., chunksize=10000)`로 수백만 행도 분할
- **메타데이터 우선** — 시트 목록·`dtypes`·5행 샘플만 먼저 보고 다음 스크립트를 결정

> **핵심 원칙:** 파일 크기와 토큰 소비는 "Python이 처리하는 한" 무관합니다. LLM이 읽는 건 오직 `print()` 출력뿐입니다.

> **참고:** 세션이 끝나면 업로드한 원본·산출물은 컨테이너와 함께 삭제됩니다(9.6). 자료는 "처리"되지만 컨테이너에 "잔류"하지 않습니다.

## 9.5 Python 런타임 — 코드 인터프리터의 실체

**보안상 외부 사이트 접속·패키지 설치(`pip install`)는 불가**합니다. 대신 실무에 필요한 패키지가 **사전 설치** 돼 있습니다.

| 카테고리 | 대표 패키지(예) |
|---|---|
| 데이터 분석 | pandas, numpy |
| 시각화 | matplotlib, seaborn, plotly |
| 문서 처리 | openpyxl, xlsxwriter, pypdf, pdfplumber, python-docx, python-pptx |
| 이미지 처리 | Pillow(PIL), OpenCV |
| 웹/HTTP | requests, httpx |
| 유틸리티 | rich, tqdm, jinja2, markdown 등 |

→ "전용 컨테이너에서 Word/PPT/Excel/CSV/PDF 산출"이 **이 사전 설치 스택**으로 실현됩니다. 설치를 막아 보안을 지키되, 실무에 필요한 라이브러리는 미리 다 넣어둔 절충입니다.

## 9.6 메모리 아키텍처 — 단기·장기 2계층

메모리의 "구조화된 노트·계층 메모리"는 실제로 **세션 메모리 저장소**로 구현됩니다. 이 저장소는 대화 턴, 작업 중간 저장점(체크포인트), 접근한 파일·참조 목록, 도구 호출 이력, 그리고 대화 전문 검색용 인덱스를 담습니다.

**두 계층으로 나뉜 메모리 (핵심):**

```
┌──────────────────────────────────────────┐
│   Microsoft 365 클라우드 (영구)            │ ← 세션 간 유지
│   · Copilot 메모리(서버사이드)             │
│   · 사용자 프로필·설정                      │
│   · SharePoint / Exchange 데이터           │
└───────────────────┬──────────────────────┘
                    │ 세션 시작 시 주입
┌───────────────────▼──────────────────────┐
│   컨테이너 작업 공간 (임시·세션 한정)      │ ← 세션 종료 시 소멸
│   · 세션 메모리 저장소 (대화 턴 기록)      │
│   · 업로드·작업·결과물 영역                │
│   · 처리한 파일·아티팩트                    │
└──────────────────────────────────────────┘
```

| 구분 | 저장 위치 | 세션 종료 후 |
|---|---|---|
| 현재 대화 턴 | 세션 메모리 저장소 | ❌ 소멸 |
| 생성 파일 | 결과물 영역 | ❌ 소멸 |
| Copilot 메모리 | M365 클라우드 | ✅ 유지 |
| SharePoint 데이터 | M365 테넌트 | ✅ 유지 |

> **비유:** 컨테이너 작업 공간은 **RAM(임시)**, M365 클라우드는 **HDD(영구)**. 컨테이너는 매 세션 새로 켜지는 RAM이라, 세션 간 기억은 반드시 클라우드(M365) 쪽에 있어야 합니다.

## 9.7 대화에 RAG를 적용한 메모리 강화

> **짚고 가기:** 9.6의 검색 인덱스는 단순 저장이 아닙니다. 컨텍스트 윈도우가 넘칠 때 과거 턴을 **검색해 꺼내오는** 장치이며, 그 검색을 가능케 하는 **경량 로컬 임베딩 엔진**이 컨테이너 안에 들어 있습니다. 즉 **대화 자체에 RAG를 적용** 한 구조입니다.

**두 개의 임베딩, 두 개의 목적 — 문서 RAG vs 대화 RAG:**

이 환경에는 **서로 다른 두 임베딩**이 공존합니다. 참조자료 검색(문서 검색)과 헷갈리면 안 됩니다.

| | M365 Semantic Index | 로컬 임베딩 |
|---|---|---|
| 위치 | Azure 클라우드 | 컨테이너 내부 |
| 대상 | SharePoint 문서·파일 | 현재 세션 대화 내용 |
| 목적 | 파일 검색·다운로드 | 세션 내 컨텍스트 검색 |
| 네트워크 | 필요 | 불필요(로컬) |

**왜 필요한가 — 컨텍스트 윈도우를 검색으로 보강:**

핵심은 "저장"이 아니라 **컨텍스트 윈도우 초과 보완**입니다. 세션이 길어지면 앞 턴이 윈도우 밖으로 밀려납니다. 이때 "아까 만든 PPT 파일명이 뭐였지?" 같은 질문을 검색 인덱스가 해결합니다.

```
컨텍스트 윈도우(단기)  →  세션 검색 인덱스+로컬 임베딩(중기)  →  M365 클라우드(장기)
   최근 N턴만 유지            초과 시 과거 턴 검색·삽입             세션 종료 후 영구 보존
```

> **결론:** "메모리 강화"가 맞습니다. 단 **저장**이 목적이 아니라, **컨텍스트 윈도우가 부족할 때 과거 턴을 정확히 검색해 꺼내오는 것**이 핵심입니다. RAG가 문서에 적용된 것처럼, **대화 자체에 RAG를 적용** 한 구조입니다.
